# Definition of done for release 1

**Current verdict: blocked.** The project is an unfunded solo proof of concept. No production gate has passed. Release 1 is ready when the owner can identify one iOS and web release candidate, link the evidence below for that candidate, and record a passing launch decision. A merged experiment establishes only its recorded result. [Current execution scope](poc-scope.md) · [Program plan, sections 4–9](program-plan-v0.5.1.md)

## What ships

Release 1 covers iOS and web on Tezos, Solana, Ethereum mainnet and Base. Users can own Solana and tz1 accounts with Ed25519 and Ethereum and Base accounts with secp256k1. Each additional owned Tezos type, tz2 through tz4, needs its own admission verdict. Both apps recognize tz1 through tz5 and offer operations according to the connected protocol. Both deliver the four-chain NFT gallery with media proxy and spam filtering. Phase 7a explanations are read-only and have no signing path. Android, owned tz5 and delegated agent actions belong to later releases. [Scope and decisions](program-plan-v0.5.1.md#5-release-1-scope)

Section 5 labels candidate features and open decisions separately. At scope commitment, record the accepted transfer, token, simulation, dApp, identity and fee policies against that table. A proposed provider or a provisional timing threshold cannot silently become a release requirement. Record later improvements in the backlog. Changing a committed requirement needs an owner decision with the effect on the relevant gate.

## Evidence for the release verdict

| Milestone | Acceptance evidence |
| --- | --- |
| G0 and G1, scope and targets | Link the charter, provenance and license records, delivery reference for the request to qualified counsel, named staffing and booked audit capacity, and the release scope that capacity supports. Link the audience and concept decision, C1 findings, approved flows and measurable G1 quality targets. |
| G2 and C2, architecture | Link the custody, recovery, legal, signing-policy and minimum-curve decisions to their tests. Obtain counsel’s opinion on the selected design and resolve required changes. TLC must find no counterexample within the section 8 bounds. Record the required architecture proofs, assumptions and counterexamples against the frozen obligations. Include recovery usability results. Every mandatory safety property needs its required proof. Only eligible liveness or performance exceptions may carry written acceptance and an unverified verdict. |
| G3 and C3, admission and exit | For each owned key type, link the pinned implementation, external assumptions review, chain verification, reference iPhone and WASM measurements, recovery and compromise tests, and funded independent review booking. Admit a type only when every check passes, including both latency budgets. Defer any optional type that fails. Both minimum curves must pass. Record the language and default Tezos type decisions and C3 latency review. Run the open-source exit tool with every project host blocked, using only the user's quorum. Demonstrate signing, export where possible, migration of transferable assets and revocable or transferable permissions, and show the user asset-specific exceptions before exit, including continued exposure at the old address. |
| Phases 4–5 and G4, shipping apps | Link enrollment, takeover, replay, concurrent recovery, revocation and lost-device results and implementation trace validation. Require rejection of every specified adversarial scenario and successful validation of every conformance and adversarial trace. The frozen operation-by-chain conformance suite must pass in full. Both apps must pass shared conformance and meet the G1 quality targets. Link evidence for the admitted account types, signing displays and refusals, NFT gallery and media handling, and the approved dApp flows. |
| Phase 7a and G5, launch | Show the read-only agent has no path to signing. Complete the independent cryptographic and protocol audit for every admitted key type, penetration testing including the media proxy, recovery and exit drills, and compromised-infrastructure exercises including malicious web delivery. Link monitoring, incident response, reproducible builds, two-person release signatures using separate hardware keys, candidate hashes in the public append-only release log and limited beta results. Close every critical or high finding using CVSS 4.0 for implementation findings and the threat model's severity scale for protocol findings. Record residual risk acceptance in writing. |

For each gate record the reviewer, verdict, evidence revision and unresolved conditions. Link the release commit and build identifiers, gate records, audit closure evidence and written risk acceptance in the launch decision. If a release-blocking requirement is unmet or its evidence is missing, record the blocker and keep the verdict open. Production release authorization stays with dvkam.
