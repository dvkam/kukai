# P3-02: Admit or defer owned Tezos tz2 accounts

| Field | Value |
| --- | --- |
| Phase | 3 |
| Type | Experiment |
| Status | Draft |
| Owner | Unassigned |
| Required roles | Tezos engineer and cryptography reviewer |
| Decision targets | No open question closes through this ticket alone. |

## Outcome

Decide whether the secp256k1 implementation also meets the requirements for an owned tz2 account.

## Blocked by

- [P3-01: Validate the minimum keys and decide derivation](p3-01.md)

## Acceptance criteria

- [ ] Use a Tezos-specific key distinct from the EVM key. Test encoding, reveal, watermark, forging and chain-native signature verification.
- [ ] Run the relevant recovery, compromise-response and independent-exit cases. Do not infer admission solely from Ethereum results.
- [ ] Record physical-device and browser feasibility and the scope of funded independent review.
- [ ] Return admit, defer or fail with evidence. If the owner declines the experiment, record deferral and preserve address support.

## Evidence

A tz2 admission report or an explicit deferral decision.

## Failure or deferral

This optional key type must not delay release of admitted minimum keys. Do not silently classify unrun tests as passes.
