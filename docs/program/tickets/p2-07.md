# P2-07: Define recovery and validate it with users at C2

| Field | Value |
| --- | --- |
| Phase | 2 |
| Type | Decision |
| Status | Draft |
| Owner | Unassigned |
| Required roles | Identity engineer, product researcher and security reviewer |
| Decision targets | Q-04, Q-33 |

## Outcome

Specify recovery and identity linking, then test whether the selected audience can complete the required flows.

## Blocked by

- [P2-06: Choose custody and enforceable web exposure controls](p2-06.md)
- [P1-04: Review G1 and retain the C2 and C3 follow-ups](p1-04.md)

## Acceptance criteria

- [ ] Define enrollment, linking, unlinking, revocation and recovery transitions for the selected custody model.
- [ ] Choose notification attempts, recovery delay, one-time dispute delay and the additional factor. Repeated objections cannot restart the delay.
- [ ] Test lost, destroyed, stolen and intermittently connected devices. Include factor loss, provider loss, concurrent recovery and an attacker holding the stolen device.
- [ ] Run recovery usability sessions against the G1 protocol. Record completion, comprehension and failure causes without real credentials or funds.
- [ ] Deliver C2 with the accepted recovery policy, user instructions and design changes. Reopen custody decisions if usability requires a different access structure.

## Evidence

Recovery state transitions, adversarial results, anonymized usability results and the C2 handover.

## Failure or deferral

Do not claim bounded recovery delay when the user lacks its required factor. Record that case and its consequences.
