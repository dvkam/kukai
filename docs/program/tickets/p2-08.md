## Outcome

Specify what the wallet displays, binds and refuses for every supported request type.

## Blocked by

- [P2-06: Choose custody and enforceable web exposure controls](p2-06.md)
- [P1-03: Set product requirements and measurable quality targets](p1-03.md)

## Acceptance criteria

- [ ] Cover native/token transfers, approvals, permits, operator grants, typed messages, arbitrary payloads, unknown calls and EIP-7702 authorizations. Define policy precedence for overlapping request types.
- [ ] Bind approval to chain, account, exact bytes, simulation context and rendering version. Define canonical encoding, expiry and behavior after account or network changes.
- [ ] Set refusal rules for failed or missing simulation, unknown decimals, unsupported payloads and disagreements between providers. Define limits without assuming an unavailable token price or decimals value.
- [ ] Gate Tezos operations by protocol capabilities. Include tz5 destinations, tz4 proof of possession, EVM network ambiguity and Solana ordinary and durable-nonce transactions.
- [ ] Write a conformance case inventory per chain and operation, including malicious metadata and state changes after simulation. Require iOS confirmation for grants regardless of immediate transfer value.

## Evidence

An accepted signing policy, typed request contracts and a versioned conformance case specification.

## Failure or deferral

Unsupported behavior must have an explicit refusal path. A successful simulation does not establish user intent or future execution results.
