# P2-01: Model trust boundaries and define the experiment suite

| Field | Value |
| --- | --- |
| Phase | 2 |
| Type | Decision |
| Status | Draft |
| Owner | Unassigned |
| Required roles | Security architect and formal methods lead |
| Decision targets | No open question closes through this ticket alone. |

## Outcome

Define attackers, signing paths and shared experiment cases before the custody experiments start.

## Blocked by

- [P0-07: Review G0 and authorize the next phases](p0-07.md)

## Acceptance criteria

- [ ] Map service-assisted signing, recovery, unilateral exit and DKG. Name every share, factor, release channel and operator trust boundary.
- [ ] Enumerate attacks against the web release, signer, coordinator, identity provider, device, recovery factor and combinations of them.
- [ ] Turn the frozen obligation list into testable requirements with preconditions and expected outcomes. Propose any refinement through the review rule from P0-06.
- [ ] Define repeatable experiments for missing participants, concurrency, replay, restore, outage and protocol upgrades. Use test keys with no real funds.
- [ ] Specify evidence storage and redaction. Never include live shares, recovery factors or personal identity tokens in traces.

## Evidence

A threat model, requirement map and shared adversarial experiment specification.

## Failure or deferral

Unclear trust assumptions block dependent decisions. Do not weaken the attacker merely to make an experiment pass.
